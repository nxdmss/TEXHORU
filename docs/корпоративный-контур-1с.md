# Корпоративный контур TEXHORU ↔ 1С

## Что включено сейчас

Текущий безопасный режим — **READ_ONLY**. Сайт читает каталог, группы, цены и остатки, но не меняет документы, справочники, цены или остатки в 1С. Конфигурация и обработка 1С этим обновлением также не изменяются.

На сервере уже подготовлены основы взрослого обмена:

- неизменяемый GUID 1С остаётся главным идентификатором товара и группы;
- запросы нового каталожного агента подписываются HMAC-SHA256;
- подпись привязана к методу, адресу, времени, одноразовому `nonce` и точному телу запроса;
- повтор подписи и запрос старше пяти минут отклоняются;
- сервер ведёт реестр устройств агента без сохранения IP в открытом виде;
- входящие события записываются в идемпотентный inbox — повторная доставка безопасна;
- будущие команды в 1С записываются в durable outbox и не теряются при перезапуске;
- новый заказ создаёт команду `ORDER_CREATE`, но она остаётся в `WAITING_APPROVAL`;
- изменение статуса заказа создаёт отдельную команду, тоже ожидающую подтверждения;
- изменение политики и действия с заданиями доступны только директору и попадают в аудит;
- сервер проверяет допустимые переходы статуса заказа и не позволяет вернуть завершённый заказ назад.

## Кто отвечает за данные

| Данные | Главный источник |
| --- | --- |
| GUID, артикул, название, группа | 1С |
| Розничная цена и остаток | 1С |
| Исполнение заказа после будущего согласования | 1С |
| Фото, SEO, тексты витрины, публикация | TEXHORU |
| Корзина, избранное, сессия покупателя | TEXHORU |
| История интеграции и аудит действий | TEXHORU |

Импорт обновляет существующую карточку по GUID. Фото и оформление сайта не должны удаляться повторной загрузкой из 1С.

## Три независимых предохранителя записи

Отправка заказа в 1С возможна только если одновременно выполнены все условия:

1. на сервере задано `ONE_C_ORDER_WRITES_ENABLED=true`;
2. директор переключил политику в `ENABLED` и включил `allowOrderWrites` с точным подтверждением `ENABLE_1C_WRITES`;
3. конкретная команда одобрена директором.

Само изменение политики дополнительно заблокировано, пока `ONE_C_ALLOW_WRITE_CONFIGURATION` не равно `true`. По умолчанию оба серверных флага отсутствуют и считаются выключенными. Сейчас их включать нельзя: сначала нужны согласование, резервная копия и испытание на копии базы 1С.

## Панель и API диагностики

После входа администратора:

- `GET /api/admin/integrations/1c/foundation` — режим, серверные рубильники, агенты, очередь и последние события;
- `PATCH /api/admin/integrations/1c/foundation/policy` — политика, только директор;
- `POST /api/admin/integrations/1c/foundation/commands/:id/action` — `approve`, `cancel` или `retry`, только директор.

Просмотр панели ничего не отправляет в 1С. Одобрение команды тоже не обходит режим READ_ONLY и серверный рубильник.

## Безопасный запуск этого обновления

1. Обновить сайт обычной командой:

   ```bash
   sudo texhoru update
   ```

2. Убедиться, что в диагностике режим `READ_ONLY`, а `orderWrites` и `policyChanges` равны `false`.
3. Обновить только каталожный агент на Windows штатным `Update-CatalogAgent.ps1`. Это обновляет транспорт агента, но не конфигурацию и данные 1С.
4. Проверить: агент онлайн, группы и товары читаются, очередь ошибок не растёт.
5. Не включать исходящие записи до отдельного согласования.

## Мини-регламент эксплуатации

- Секрет `ONE_C_API_KEY` не отправлять в чат и не хранить в скриншотах.
- Для основной и тестовой базы использовать разные ключи и разные `baseId`.
- Перед изменениями интеграции делать резервную копию PostgreSQL и копию базы 1С.
- Сначала проверять новую схему на копии 1С, затем проводить ограниченный пилот на одном заказе.
- При инциденте первым действием вернуть политику в `READ_ONLY`; вторым — выключить серверные write-флаги; третьим — отключить устройство агента.
- Не очищать очередь вручную: отменять задания через действие `cancel`, чтобы остался аудит.
- Раз в неделю просматривать ошибки inbox/outbox и неизвестные устройства, раз в квартал менять ключ агента.

## Что потребует отдельного согласования

Следующий этап — запись заказов в тестовую копию 1С, сопоставление контрагентов, видов оплаты, доставки, складов и статусов. До утверждения этих правил сервер продолжает только читать данные 1С и безопасно накапливать неподтверждённые команды.
